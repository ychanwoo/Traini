# Garmin 활동과 훈련 완료 연결

## 연결 기준

계획의 시간대에서 활동 시작 시각을 훈련 날짜로 변환합니다. 업로드 때의 시간대나 UTC 날짜를
그대로 비교하지 않으며, 미래 활동·다른 사용자·휴식일·건너뛴 훈련은 연결하지 않습니다.
`garmin_fit` 원본/정규화 provenance가 있고 거리·타이머가 양수인 러닝만 연결할 수 있습니다.
소유자·계획·활동의 일관성은 서비스 함수와 DB 트리거에서 확인합니다.

자동 연결은 그 날짜에 활동이 하나이고, 계획 거리의 ±10% 이내일 때만 시도합니다.
이는 자동 연결용 휴리스틱이며 훈련 효과나 목표 달성을 평가하는 기준이 아닙니다.

- 회복런·이지런·롱런: 거리 기준에 더해 명확한 고강도 반복 구성이 없는지 확인합니다.
  구조화된 지속주도 본운동이 계획의 편한 페이스와 비슷하면 연결할 수 있습니다.
  회복런은 현재 계획 스키마의 `easy`로 저장하고 목적·제목·페이스를 구분합니다.
- 템포런: 완전한 랩 근거, 워밍업·쿨다운, 활성 구간 거리와 본운동 페이스를 확인합니다.
- 인터벌: 반복 거리·횟수·사이 회복 거리·필요한 마지막 회복을 확인합니다.
  400m/800m를 고정 처방하지 않으며 계획에 명시된 반복 구성을 기준으로 비교합니다.
- 품질 세션은 활성 구간이 쉬운 구간보다 구별되게 빨라야 합니다. 일반 FIT `interval` 라벨만으로
  고강도 훈련으로 분류하지 않습니다. 데이터가 부족하면 자동 추측 대신 확인 상태로 둡니다.

여러 활동을 임의로 합치지 않습니다. 오늘·일정의 **Garmin 기록 확인**을 펼쳐 워밍업·본운동·쿨다운
등 해당 활동을 직접 선택해 완료를 확인할 수 있습니다(최대 12개). 거리나 세션 조건이 다른
기록을 선택하는 것은 사용자의 명시적인 확인이며, 자동 판정과 별도로 `confirmed`로 기록합니다.
이미 다른 훈련에 사용한 활동, 잘못된 날짜, 미검증·거리/시간 누락 기록은 수동으로도 연결할 수 없습니다.

## 상태와 저장

`workout_activity_matches`는 활동 하나가 여러 훈련에 중복 연결되지 않도록 활동 UUID를 기본 키로
사용합니다. 여러 활동을 한 훈련에 연결하는 것은 지원합니다. 자동/직접 확인 방법과 활동 revision,
활성 상태를 별도로 저장합니다. 단일 활동 연결만 기존 `completed_activity_id`에도 반영합니다.

기존 완료는 `manual_completed_at`으로 보존합니다. 실제 기록 확인 완료와 직접 표시 완료를
UI에서 구분합니다. 연결 해제나 기록 변경이 있어도 수동 완료는 지우지 않습니다. Garmin 근거만으로
완료했던 경우 근거가 무효화되면 자동 완료를 해제하고 확인 상태로 되돌릴 수 있습니다.
연결 해제는 해당 훈련의 자동 재연결을 중지하며, 직접 다시 연결할 수 있습니다.
이전 연결은 비활성 행으로 남기되 원본 활동/계획 삭제 시에는 FK에 따라 제거됩니다.
날짜가 수정된 활동의 비활성 연결은 새 날짜의 훈련으로 직접 확인해 옮길 수 있습니다.
활성 연결을 다른 훈련이 가져가거나 비활성 연결을 자동으로 재배정하지 않습니다.

실제 거리와 계획 거리는 합산하지 않습니다. 일정의 진척 거리는 완료한 훈련의 **계획 거리**이고,
연결 상세에는 실제 거리를 별도로 표시합니다. 전체 실제 거리는 주간 러닝 요약이 기준입니다.
기록이 없다는 사실만으로 미수행·휴식이라고 판단하지 않습니다.

## 재가져오기·동시 요청

일관된 bounded DB snapshot을 읽고 순수 TypeScript 규칙으로 결정한 후, revision을 다시 확인해
한 트랜잭션으로 적용합니다. 동시에 수집·재생성·수동 완료가 일어나면 소유자 advisory lock과
revision 검사로 충돌을 막습니다. 자동 재검증은 충돌 시 한 번 다시 읽으며 수동 요청은 409로
새로 확인하도록 안내합니다. 실패한 결정 묶음은 전부 롤백합니다.

원본/정규화 hash, 시각·거리·시간·페이스·랩 근거가 바뀌면 재검증합니다. 단순한 동일 파일 재업로드는
연결을 중복 생성하지 않습니다. 직접 확인했던 기록이 바뀌면 다시 확인하기 전에는 자동 승인하지 않습니다.
활동 내용이 수정된 뒤 이전 근거를 계속 신뢰하지 않으며, 단순 처리 타임스탬프만 바뀌는 것은 제외합니다.

가져오기 결과가 저장되면 브라우저가 `/api/training/match/reconcile`로 최근 8개 완료 주와 이번 주의
계획을 확인하고 오늘·일정을 갱신합니다. 부분 실패한 가져오기도 저장된 활동만 확인합니다.
연결 확인 실패는 가져오기 실패로 바꾸지 않으며 별도 안내와 재확인을 제공합니다.
화면을 닫았다면 다시 열 때 결과를 확인합니다. 오늘/일정 조회도 해당 계획을 재검증합니다.
CLI 업로드 후에도 화면에서 상태를 확인할 수 있습니다. 별도 상시 백그라운드 스케줄러는 추가하지 않습니다.

계획 조회 중 연결 확인이 실패하면 저장된 계획과 완료 상태를 유지하고 확인 지연을 표시합니다.
잘못된 snapshot이나 과도한 데이터는 기록 없음으로 처리하지 않습니다. 한 주 활동 100개,
한 계획 훈련 7개, 한 번의 과거 계획 확인 9주, DB 병렬 요청 3개로 제한합니다.

## 세션 생성 보강

AI 프롬프트에 회복·이지·롱런·템포·인터벌 각각의 목적, 거리와 페이스 근거를 요구합니다.
템포 페이스를 인터벌 전체 평균으로 추정하지 않습니다. 회복런은 편한 목적과 페이스로 구분합니다.
검증기는 편한 훈련의 페이스 상한, 주간/단일 거리, 품질 훈련 빈도·거리, 휴식 간격을 유지하며
템포의 본운동 누락과 고강도 세션의 워밍업·쿨다운 순서도 거부합니다. 기존 계획을 자동 재생성하거나
추가 AI 호출을 하지는 않습니다. 수행 결과를 다음 계획에 체계적으로 반영하는 주간 리뷰는 다음 이슈입니다.

## 설정과 검증

`20261016040000_garmin_workout_matching.sql`을 적용합니다. 기존 활동·계획·완료 데이터를 삭제하지
않으며 새 테이블은 관리자 본인 읽기, 서버 함수는 service role 실행만 허용합니다.

```sh
npm run test:matching
npm run test:matching:integration
npm run test:db:matching
node --test tests/*.test.mjs
npm run test:db:plan
npm run test:db:lap
npm run test:db
npm run test:db:admin
collector/.venv/bin/python -m unittest discover -s collector/tests -q
npm run lint
npx tsc --noEmit
npm run build
```

실제 DB 통합 검증은 임시 계정을 사용하며 실제 관리자의 활동·목표를 수정하지 않습니다.
기존 FK 정리 순서를 고려해 임시 계획 → 활동 → 계정 순서로 제거합니다. 이메일·토큰은 출력하지
않고 Garmin 다운로드나 AI 생성은 호출하지 않습니다. SQL 검증은 모든 fixture를 롤백합니다.

## 구현 당시 검증 기록

Node 145개·Python 103개 테스트, 매칭/관리자/활동 저장/주간 계획/랩 근거 SQL 검증 5종,
실제 DB 연결 통합 테스트와 HTTP 인증 회귀, lint·TypeScript·프로덕션 빌드를 통과했습니다.
동시 재검증, 날짜 수정 후 명시적 재연결, 실패 배치 전체 롤백을 확인했습니다.
오늘·일정의 기존 수동 완료와 320/375/430/768px 화면 폭을 확인했고 기존 관리자 활동을
유지했습니다. 임시 매칭 계정과 데이터는 제거했습니다. 추가 AI 생성 요청은 실행하지 않았습니다.
