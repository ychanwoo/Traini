# 목표와 러닝 기록으로 구성하는 훈련 입력 데이터

이 단계는 OpenAI를 호출하거나 훈련계획을 생성하지 않습니다. 기존 프로필의 목표와
실제 저장된 Garmin FIT 활동을 일관된 구조로 읽어 다음 계획 생성 단계에 전달합니다.
화면의 준비 여부는 **입력의 완성도**이며 신체 상태·훈련 적합성 판단이 아닙니다.

## 저장 구조와 목표 편집

기존 `profiles`의 `race_name`, `target_distance`, `target_date`, `target_time_seconds`를
재사용합니다. 마이그레이션 `20261016000000_add_training_availability.sql`은 다음 두 컬럼만
추가하며 기존 값·UUID·이름·생성일·RLS를 바꾸지 않습니다.

- `training_days`: ISO 요일 배열(월=1, 일=7). 중복·범위 밖 값·NULL 원소·다차원 배열은 거부합니다.
- `long_run_day`: 훈련 가능한 요일 중 장거리 훈련 선호 요일. 설정되지 않았으면 NULL입니다.

기존 사용자에게 요일을 임의로 채우지 않습니다. 요일을 모두 해제하면 NULL로 저장하고
장거리 요일을 해제하면 다른 요일을 자동 선택하지 않습니다.

`/my/goals`와 `/goal-setting`은 동일한 편집기를 사용합니다. 저장된 목표를 읽기 전에는
편집/저장을 비활성화하고, 조회·저장 실패를 성공으로 표시하지 않습니다. 네트워크 오류 시
입력값을 유지합니다. 예시 대회·목표 기록·예상 기록은 실제 목표로 채우지 않습니다.

목표 거리(5K/10K/HALF/FULL), 미래의 목표 날짜, 훈련 가능 요일과 장거리 요일을 입력
완성도에 반영합니다. 대회명과 목표 기록은 선택입니다. 목표 기록은 HH:MM:SS, 분·초는
0~59이며 양수 시간만 허용합니다. 종목별 임의 기록 제한이나 예상 완주 기록은 적용하지 않습니다.
빈 항목을 포함한 초안 저장은 허용하고 컨텍스트에서 누락 항목을 별도로 표시합니다.
기존 목표가 만료됐거나 형식이 잘못됐으면 정상값으로 가정하지 않고 문제 항목으로 반환합니다.

## API

- `GET /api/training/goal`: 저장된 목표, 기존 값의 문제, 서버 훈련 시간대와 오늘 날짜.
- `PUT /api/training/goal`: 전체 목표 필드를 검증해 기존 프로필만 수정. 임의 사용자 ID나 추가 필드는 거부.
- `GET /api/training/context`: 목표와 완료된 최근 8주의 러닝 입력 데이터.

모두 서버가 검증한 관리자 Bearer 토큰이 필요합니다. 다른 사용자/미인증 요청은 저장소에
접근하지 않습니다. PUT은 Origin·JSON 형식·본문 크기(8KiB)를 확인합니다. 저장 성공은
실제 수정된 프로필 행이 확인됐을 때만 반환하고 프로필을 자동 생성하지 않습니다.

응답은 `private, no-store` 및 `Vary: Authorization`을 사용합니다. DB 오류·서비스 키·
프로필 UUID·이름·사진·GPS·원본 JSON은 반환하지 않습니다. 조회 실패는 503이며 빈 기록과 구분합니다.
컨텍스트 시간대/소유자/조회 주수는 클라이언트가 지정할 수 없습니다.

## 컨텍스트 계약 (schemaVersion 1)

`TRAINI_TIMEZONE`(기본 America/Los_Angeles)에서 오늘과 완료된 지난 월~일을 결정하고,
그 주를 포함한 8주를 조회합니다. 이번 주는 부분 주간이므로 과거 기준에 포함하지 않습니다.
UTC 조회에 작은 여유 구간을 더한 뒤 실제 UTC 시작 시각을 훈련 시간대로 변환한 날짜로
정확하게 재분류합니다. DST 전환에도 고정 168시간으로 주간을 계산하지 않습니다.

`goal`에는 실제 설정, 거리(m), 오늘부터 목표일까지의 달력 날짜 차이가 들어갑니다.
`planningPeriod`는 오늘부터 목표 날짜까지이며 누락/만료된 목표를 임의의 훈련 기간으로
대체하지 않습니다. `inputs.issues`가 잘못됐거나 빠진 목표를, `inputs.limitations`가 기록 부족과
누락 지표를 설명합니다. `readyForPlanInput`은 목표 필수 항목이 유효하고 거리·타이머가 함께
있는 양수 러닝 기록이 하나 이상일 때만 true입니다. 8주가 모두 있어야 한다는 뜻은 아니며
기록이 부족하다는 사실은 별도로 유지합니다.

`history`는 저장된 FIT 러닝만 포함하며 주간별로 다음을 반환합니다.

- 기간, 활동 횟수와 러닝한 날짜 수
- 거리 합계(m), 타이머 시간 합계(초), 최장 거리(m)
- 거리와 타이머가 함께 있는 활동의 가중 페이스(초/km)
- 거리·타이머·페이스·심박 정보가 있는 활동 수

기록이 없는 주는 `no_recorded_activities`이고 거리·시간·페이스·최장 거리는 NULL입니다.
이는 실제 휴식 주간이나 0km 훈련으로 확정한 값이 아닙니다. 반대로 저장된 활동의 0m/0초는
0으로 보존합니다. 누락 지표는 다른 지표나 다른 활동의 수치로 대체하지 않습니다.
심박이 없으면 추정하지 않고 해당 지표의 coverage를 줄입니다. 수면·HRV·회복 데이터는
이 컨텍스트에 포함하지 않으며, 회복 준비도를 만들어내지 않습니다.

페이지당 500행을 요청하고 서버가 더 적게 반환해도 실제 개수만큼 진행합니다. 최대 10,000행,
전체 프로필/활동 조회 15초 제한을 두며 페이지 수 변경·누락·중복·비정상 수치는 실패 처리합니다.

목표를 저장하거나 Garmin 가져오기가 저장 단계를 마치면 열려 있는 데이터 카드가 다시 조회됩니다.
포커스 복귀와 주기적 갱신으로 날짜 경계도 반영합니다. 기존 프레임·색·타이포그래피를 유지합니다.

## 검증과 실행

```sh
npm run test:training
npm run test:admin
npm run test:summary
npm run test:garmin
npm run lint
npm run build
```

실제 DB에는 정상 마이그레이션 흐름으로 적용합니다. 기존 DB를 reset하지 않습니다.
제약조건 SQL 테스트는 트랜잭션 전체를 롤백해 기존 목표·요일을 보존합니다.

```sh
npx supabase db push --linked
npm run test:db:training
```

2026-10-15 태평양 시간 기준 실제 기록은 8주 중 1주, 러닝 6개입니다. 미설정 훈련 요일을
표시하며 기록이 없는 나머지 7주를 휴식으로 계산하지 않는 것을 확인했습니다.
요일 선택/해제 연동, 잘못된 시간 입력 차단, 실제 목표 저장, 저장 후 컨텍스트 갱신을
브라우저에서 확인했습니다. 사용자의 훈련 요일을 테스트 값으로 저장하지 않았습니다.

## 하단 네비게이션 변경 (별도 UI 커밋 대상)

인증된 앱/설정 화면과 Garmin·목표·분석 화면의 공통 레이아웃에 같은 메뉴를 둡니다.
각 화면의 개별 메뉴를 제거해 중복 표시를 막고 기존 430px 폭과 safe-area 여백을 유지합니다.
로그인/스플래시에는 메뉴를 추가하지 않습니다. Garmin·목표·분석·계정 상세 화면은 마이 탭에 속합니다.

## 이후 개발 순서 (주간 계획 생성 우선)

사용자와 합의한 순서: 이미 생성한 이슈와 feat/weekly-training-plan 브랜치의 원래 범위부터 진행합니다.
쿠키 기반 서버 세션·Proxy 보강은 다음 별도 이슈로 분리하며 이번 브랜치에 합치지 않습니다.

1. feat/weekly-training-plan: AI 연결·과금 방식을 확인하고, 기존 목표·훈련 가능 요일·최근 러닝 기록으로 주간 훈련계획을 생성합니다. OpenAI 결과를 검증하고 기존 Supabase training_plans/workouts에 안전하게 저장해 일정·오늘 화면의 예시 훈련을 실제 계획으로 교체합니다. 수동 생성 버튼, 중복/동시 호출 방지, 요청 제한, 사용량·비용 기록, 실패 시 기존 계획 보존과 테스트를 포함합니다. 기존 서버 관리자 UUID 검증은 유지하고 AI 호출 직전에도 수행합니다. OPENAI_API_KEY 방식의 별도 과금과 공식 ChatGPT 구독 연동의 적용 조건은 실제 연결 전에 확인합니다.
2. 인증·권한 보강 별도 이슈: 서버가 읽는 쿠키 기반 세션과 Next.js 16 Proxy를 구성하고 비로그인/비관리자의 URL 직접 진입, 페이지·데이터·API 직접 접근을 검증합니다. 로그인·콜백·정적 자산은 필요한 범위로 허용하고 기존 API 관리자 검증을 유지합니다.
3. Garmin 실제 러닝과 계획의 완료/미완료 상태를 연결합니다.
4. 주간 수행 결과를 리뷰해 다음 주 계획 갱신에 반영합니다. 예약 자동 실행은 수동 흐름 검증 후 별도로 구현합니다.
5. 기존 WEATHER_API_KEY와 날씨 코드를 확인해 당일 날씨 보정을 연결합니다. 날씨 조회 실패 시 기본 계획은 유지합니다.
6. 남은 프로토타입 수치를 실제 데이터로 교체하고 운영·복구·포트폴리오 문서를 정리합니다.

각 작업은 이슈와 브랜치로 나누고, 기존 디자인·430px 모바일 프레임을 유지합니다.
다음 구현 시작 시 feat/weekly-training-plan 브랜치와 작업 트리를 먼저 확인합니다.
이 순서 기록만으로 구현·커밋·push를 실행하지 않습니다.


## 2026-10-16 구현 상태

feat/weekly-training-plan에서 구독 연결 확인, 스트림 완료 확인, 계획 검증, 트랜잭션 저장,
오늘·일정 반영과 수동 완료 저장을 구현했습니다. 입력이 같은 주 계획은 재사용하고, 입력이
바뀌면 재생성하되 과거 날짜와 완료한 훈련은 보존합니다. 최근 8주 FIT의 랩 근거를 별도로
저장해 반복 구간·회복·워밍업·쿨다운을 포함한 계획을 생성합니다. 다음 작업은 위 순서의 2번(서버 세션·Proxy·관리자 접근)입니다.
상세 계약과 커밋 분리는 [주간 계획 안내](../../docs/weekly-training-plan.md)를 따릅니다.
